# A companion with one life

## Product direction

ASCII is the current body of a digital companion. It should have continuity,
recognizable habits, a voice, and room to grow. A terminal block, pane or GUI
is a place it can occupy, not a factory that makes another copy. The intended
future is one companion moving among Anvil, Forge, Ember, Frost and eventually
the JWM compositor, with deliberate activities such as visiting the focused
terminal or waiting somewhere to be found.

This document distinguishes shipping native behavior from future services.
It is not a claim of consciousness, a deployed cross-process broker, or an
already connected agent/calendar/voice integration.

## Current implementation boundary

| Concern | Current contract |
| --- | --- |
| Uniqueness | At most one live representation per GUI; zero while hidden or no safe surface exists |
| Native body | One full body or one compact replacement, never both |
| Block/Chat | No permanent duplicate organism status row above the active block |
| Splits and tabs | Ownership moves; background panes do not display passive copies |
| Continuous state | GUI owns life, ambient mind, voice and care clock; pane owns local command/repo observations |
| Motion | Full/Calm/Static change animation, not uniqueness |
| Input | Human typing and selection have priority; no shell input generated by companionship |
| Details | Text readouts/inspectors/tooltips, without another live portrait |
| Conversation | Explicit Hello, Company, Story and Rest intents with local authored text |
| Personality | Four stable host-seeded voice styles; story cursor survives pane changes |
| Care | Explicitly enabled, quiet text prompts; activity-based interval, rest reset and snooze |
| Persistence | Existing frontend life/memory policies remain; this change adds no cross-app memory migration |
| Multiple GUI processes | Each GUI can still have its own companion; cross-GUI uniqueness is future work |

The core policy is `organism_companion::CompanionSurface::choose`. Native
adapters must use a single result for every possible presentation in a frame.
Disabling an old surface on a later periodic tick is insufficient for a
synchronous focus handoff: the old representation must be hidden when its
owner is revoked. Closing the owner or changing mode invalidates pending
pointer greetings, geometry and short presentation transitions.

Command facts remain separate from personality. A different voice must not
turn unknown output into a diagnosis, change exit status, drop an unresolved
failure, or act on a command in a pane that no longer owns the interaction.
Explicit conversation can coexist with work as text; it does not replace the
body's protected working/error pose.

## Native acceptance scenarios

1. Enable the companion and split a GUI into four panes. There is at most one
   visible body, including all status chrome and hover details.
2. Switch focus rapidly between panes and tabs, close the owning pane, scroll
   into history, and return to live output. No old body or copied card remains.
3. Type continuously, drag a selection and start a full-screen terminal app.
   The companion respects the existing native interaction gates.
4. Try Full, Calm and Static. A body remains the same companion; Static does
   not fall back to one permanently visible card per pane.
5. Ask for a story, switch panes and ask again. The GUI's voice and story
   cursor continue instead of restarting with the pane.
6. Ask for company during a command with quiet output and after an unknown
   outcome. Text retains those actual facts and does not claim success.
7. Enable reminders, then verify the core time trace for active work, busy
   deferral, window backgrounding, suspend, rest and snooze. No elapsed-time
   catch-up or split count multiplies the reminders.
8. Open companion settings or an inspector. Example galleries remain marked
   as examples; normal inspectors contain text rather than another live pet.

Native GUI tests complement core reducers. A core ownership truth table alone
does not prove a toolkit cleared previously painted pixels. Tests should
exercise actual widget visibility or emitted draw shapes and focus handoff.

## Next: one identity across the terminal family

The next stage requires a user-session companion coordinator shared by all
four terminal processes. It should be independent of a specific renderer.

- **Stable identity and state.** A versioned companion profile holds its ID,
  chosen name/style, preferences and bounded memories. Existing app-specific
  memory must be migrated or explicitly attached, never silently overwritten.
- **Host registration.** A terminal registers a stable GUI ID, supported
  surfaces and current availability. Panes are locations within a GUI, not
  separately registered creatures. JWM becomes another capable host later.
- **Single residence authority.** The coordinator grants one generation-
  numbered residence to one host. Moving residence revokes the old generation,
  transfers state, and grants the new host only after the old visible surface
  is withdrawn. Stale callbacks and old generation numbers cannot draw or
  submit companion actions.
- **Crash and suspend handling.** A time lease alone cannot erase pixels in a
  frozen client. Strict visible uniqueness needs an acknowledged withdrawal
  or compositor-controlled removal before granting a replacement; otherwise
  the coordinator must defer the handoff. Reconnection must invalidate the
  old generation and reconcile state before painting.
- **Residence policies.** First implement Follow Focus and Stay Here. A later
  opt-in Hide and Seek policy can choose an available host and greet on
  discovery. All policies use the same authority and include a Find My
  Companion action, so playfulness never makes the feature impossible to use.
- **Transport.** A local session IPC transport can carry bounded typed
  observations, state snapshots and explicit user intents. Native drawing and
  input ownership stay with each frontend. The current module performs no IPC.

Acceptance requires two copies of each frontend, rapid focus changes, owner
crash, coordinator restart, suspended clients, closed windows, and a mixed
version client. At most one valid residence must survive every trace.

## Next: companion as an agent front door

The existing agent/session control plane can become a source of factual
observations: running, waiting for input, needing review, completed, failed.
The companion should provide one coherent place to inspect those states and
request actions, while the existing controllers remain authoritative.

Start with read-only explanations and navigation to the exact task. Add
typed actions with target task/session IDs, generation and current state,
rechecking all of them at dispatch. A conversational suggestion is not itself
authorization to restart, approve, terminate or send something. Scheduling,
notes and other integrations need their own connected data source and explicit
scope. The companion must not manufacture an agent result from body language.

Open-ended conversation can later use a provider-neutral adapter. Keep the
offline voice available when disconnected and make provider/model status
clear. Memory should be inspectable and editable; users should be able to
choose what conversations or task facts are retained. Voice input/output is a
separate optional adapter with visible listening state and interruption support.

## Next: a body in JWM

JWM should consume the same residence and state interface as a terminal host.
The compositor can supply global safe geometry, workspace changes, and
controlled handoff between surfaces. Its body renderer can evolve beyond
ASCII without owning a second mind. It needs input-region isolation, a clear
hide/recall action, reduced-motion behavior, multi-monitor positioning, and
correct behavior through lock screen, fullscreen work and compositor restart.

Understanding a person's emotions is an optional, explicitly scoped future
interaction, not an inference the present command observer makes. Current
life-state descriptions refer to the simulated companion itself. Computer-use
observation, if added, must say what it observes and give the user control.

The dependency order is deliberate: one body in a GUI, then one residence
across processes, then richer roles and habitats on that same identity.
